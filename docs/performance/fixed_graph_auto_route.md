# 同一张图中的设备自动选路

本次在已验证的 `low_miss_skip` 上增加自动选择。图中的节点、输入输出
地址及 KV/Index 布局不变。决定模式和保存反馈都放在现有内核中；CPU
只提供调度时已经知道的请求身份、轮次和有效 query 数，不读取 NPU
计数来决定路线。功能默认关闭，仅支持本次验证的 URMA streaming
ready-batch 路径。

## 为什么需要选择，以及选择能解决多少问题

20 节点 NPU4 的上一轮实测如下；时间单位为 μs，按首次 high 结果
比较，不挑更快的末尾结果。输入为 BS16、Q4、127K prompt 对应的
真实 Q/Index 和合成 656B KV。

| 负载 | 强串行 mean/p50 | 精简 mean/p50 | 融合 mean/p50 | 当前较优模式 |
|---|---:|---:|---:|---|
| G2 | 335.778/334.412 | 395.453/395.419 | 430.491/431.291 | 精简 |
| G7 | 819.018/817.675 | 850.360/847.603 | 686.919/684.110 | 融合 |
| G10 | 427.587/427.996 | 461.222/460.763 | 446.061/443.144 | 融合 |
| G17 | 584.262/585.183 | 612.145/612.962 | 501.887/498.547 | 融合 |
| G4 | 500.308/500.547 | 521.080/521.622 | 441.549/440.241 | 融合 |

G4 的 high 首尾漂移为 mean +5.08%、p50 +5.66%，小于这一数量级的
差别不能单凭一次测试归因给代码。即使总能选中表中的较优模式，也
没有达到相比强串行降低 35%：G2/G10 仍慢于串行。自动选择减少的是
选错路线的损失，不会删除两条路线共有的 init、精确规划和 Index
更新成本。后续应根据完整链实测继续压缩这些成本。

## 设备上如何作决定

每个层组独立持有 `AutoRouteState`。其中每个稳定 owner 只存一条
128B 反馈：请求代号、上次成功 step、必要的去重 Get 数、有效 Q 数、
query 历史长度之和、token 字节数和上次模式。不储存或扫描全部
hot cache/Index 来作预测。

一次图执行按以下顺序进行：

1. 现有 init 的 block 0 读取请求元数据和匹配的历史。
2. 用 `ceil(前轮必要Get × 本轮Q / 前轮Q)` 预测当前请求的读取量，
   汇总预计字节数，并计算当前所有有效 query 的历史长度之和。
3. 比较 `预计字节数 × 1024 / 当前query历史长度之和` 与切换门槛，
   把统一模式写入已有 admission controls。其余 init block 不读取
   尚在更新的 controls；它们仅使用不可变配置。init 结束后的既有
   kernel 依赖边界保证 LI 看到完整决定，不新增跨 block 等待。
4. 低模式跳过早阈值和投机窗口，高模式沿用原融合。两者都完成全
   历史计分、精确 TopK、最终 Get、缓存更新和输出。
5. 现有收尾确认该请求的 Get 和 Index 更新成功后，保存本轮真实
   需求，供下一轮读取。

必要 Get 的定义为：最终独立补取数 + 最终 Q4 结果实际引用的去重
预取槽数。它包括为修复被覆盖 hot 槽而必须补取的数据，排除未被
最终结果使用的预取。它是传输需求，不等同于原始 cold miss 百分比。
这可避免“误预取越多，预测器越认为下一轮需要高模式”的错误反馈。

默认低/高门槛为 128/192，形成滞回区间：原来高模式时，需求足够
低才进入低模式；原来低模式时，需求超过较高门槛才退出。未知请求
或混合模式批次优先高模式。这两个值是当前 A5/656B 回放的试验
起点，依据 G2 与 G10 的交叉区间设置；不是跨 BS、NUMA、硬件、
token 宽度自动最优的证明。读取分布和预取精度也影响时间，目前
模型没有声称完全描述这些因素。

## 请求变化、错误和捕图

- 稳定 owner 是缓存槽位，不是永久请求身份。槽位分给新请求时，
  调度器必须增加 generation；新代号先走融合，成功后建立新历史。
  缓存重建或重新 prefill 导致旧缓存状态失效时也应增加 generation。
- 同一请求在 batch 中换行，历史跟随 owner，不跟随 batch 行号。
- step 重复、倒退、旧 generation 和身份不匹配时不学习。
  step 超过允许间隔时本轮不使用旧预测，成功后可以建立新基线。
- 当前 Q 数变化按比例估计；当前历史长度参与决策。token 字节宽度
  改变时先走高模式，重新积累同宽度反馈。
- 低估时最终 Get 仍取回全部实际 miss；不截断请求、不沿用旧 TopK。
  高估时执行了不划算的投机工作。两者影响性能，不改变正确结果。
- Get/Index 报错不提交本轮反馈。捕图、预热及人为重复运行必须置
  `learning=False`，不能伪造 decode 历史。

Python 提供固定地址的 `requests/config/feedback/pending`，通过
`set_requests` 和 `set_learning` 在图外排入同一 stream。setter 不做
设备计数读回，不调用 synchronize。必须与图执行按序提交；一份
状态不得跨独立层组或并发 stream 共用。URMA Context ABI 从 13/336B
变为 14/344B，仅追加可选状态指针；旧二进制会被明确拒绝。KVAF 和
UBmem ABI 不变。

本版状态按固定 captured batch 分配；支持同一 batch 内请求换行及
有效 Q 变化，没有实现跨不同 captured-BS 图共享一份历史。Q/历史
归一化是负载代理，不代表有 padding 的内核耗时一定按有效 Q 线性
变化；本轮性能验证仍限定实测的 BS16/Q4。

## 回放计量边界

沿用既有 diagnostics replay。强串行、强制低、高及 auto 对同一
快照比较；auto 每次恢复测试输入但保留预测反馈。捕图/预热不学习，
正式 step 1 从未知历史开始，之后仅使用设备真实成功记录。输出
既包含冷启动的完整 mean/p50，也单列后续轮次；决策与反馈写回在
NPU Event 内，输入恢复、元数据 H2D 和正确性读回在计时外。

同图生命周期验证检查重复/倒退 step、请求代际变化和真实 packed
row 重排，并保持最终分数、TopK、KV 和 Index 校验。CPU 测试覆盖
失败不提交反馈；不会为测试主动制造 URMA 硬件故障。五个冻结输入
的重复回放不代表已经验证真实服务中连续 100 轮的预测收益。

验证应同时看 auto 相对相应强制模式的开销、首尾 control 漂移、
mean 和 p50，以及相对强串行的最终差距。没有 NPU 测量前，不报告
新选择器的加速比，也不承诺已经达成 35%。
