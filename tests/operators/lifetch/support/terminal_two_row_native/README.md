# Two-row private terminal experiment

This standalone CANN target exercises a fixed-size BS32 Q4 terminal path on a direct KVAF lease. It consumes the existing four-rank LI output. Build the target from this directory alone. The production CMake graph and normal Python entry points do not reference it.

At configure time, `prepare_overlay.py` copies the pinned terminal row routine into the build directory. The experiment uses its original final TopK, ownership claims, slot assignment, descriptor write, completion-marker positions, public output and Index updates. Each query records the original SQ head, CQ cursor, cuts, row, generation, owner and retirement inputs when preparation finishes. The second row can write its descriptors and Index without ringing a doorbell. Only the original four consumers may acknowledge their queues.

The first row can claim a waiting row when all four queries have long lists, four private first completions are still unseen after all Index work and a 32 µs calibrated delay, and a successor is available. Each consumer may have two published cuts when ring capacity permits it. A prepared second row may ring its first doorbell after every first-row Q has consumed its third cut or its final shorter cut. The experiment drains both rows' final queues before team retirement. Q2 has one opportunistic check of its original prefetch queue and uses the original completion routine. If outstanding prefetch CQEs would block, it does the normal completion at retirement.

Construct `BoundJointTerminal` outside capture with a live forward binding and the standalone bridge. The explicit `launch` method replaces only the terminal dispatch in a caller that has already issued LI in the same stream. It retains its workspace and checks each lease view, backing storage range and window-independent ownership. The kernel rechecks dynamic owners and output routes on every invocation. It supports the identity routes exercised in this study. The caller owns all stream error handling and lifetime requirements of the normal lease.

`test_resume.cpp` exercises the same inlined queue operations used by the device. `test_routes.cpp` runs the same dynamic route check and uses the same `Args` and `Context` layouts. `test_lease_guard.py` tests the capture-time allocation checks. Given the archived G7 fixture's input, event and byte-oracle files, `test_archive.cpp` verifies every descriptor, payload and completion using the shared queue state machine. `faults.py` injects six corruptions into that fixture. The host tests exercise alternative physical timing through supplied CQ readiness. Board timing and end-to-end correctness of the experimental terminal still require actual hardware.

The small CANN CPU-model target in `camodel/` executes the actual joint four-core coordination, KVAF private queues and Q2 completion with two archived G7 row geometries. Its fixture substitutes row preparation and provides acknowledgment readiness, allowing the host to check issued prefix counts, original head, SQ/CQ cursors and release decisions on normal, failed and missing CQE paths. Full-device compute, real transfer latency and NPU speedup require separate measurement.

For the B24 frozen-replay fixture, the bound Index and KV tensors include a sentinel physical owner 0. The 32 requests own rows 1 through 32. The capture guard checks that the Index, bitmap and registered output each hold all 33 rows. The live device check accepts row-major owner IDs beginning at 0 or 1 and verifies output routes each invocation. The public binding's legacy `q_workers` field is independent of the four private terminal queues; the guard verifies `finalWorkers` and the 128 captured final views.

`two_row_tail.prepare_tail` builds or loads the isolated shared library and creates a separate mailbox for each captured state. Its `forward` calls the existing hot/LI cold launch pipeline and supplies a synchronous three-argument terminal callback. That callback records the distinct mailbox address in the actual CANN kernel launch. `readback` after synchronization validates the dynamic route and the four-query handshakes for each row pair. A zero-pair call is a valid outcome if none of the real queues met the wait condition.
